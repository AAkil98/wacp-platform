# v0.1.0 Gate Enforcement — Plan

> **Triggering finding:** ROADMAP.md §Pre-`v0.1.0` > Quality gates — three of the four bullets are advisory (Codecov measures but doesn't enforce; mutation pipeline runs cron-only without PR gating; coverage floor "settles" without a settle-trigger). Plan flips them to blocking. Bundles HEALTH-LOG §17 "Prevention" follow-up (`list_segments_in` sort-lift + `fs::read_dir` audit) since it's the same shape of CI-hardening work.
> **Target branch:** `ci/v0.1.0-gate-enforcement` (topic).
> **Rough effort:** ~4–7h across 5 execution phases — medium-low confidence (P2 mutation-gate path is a design decision; P3 audit may surface 0–6 fix sites depending on what each `read_dir` caller assumes).
> **Not in scope:** the actual v0.1.0 tag push, OCI publication ceremony, `:latest` regex fix (these become safe to do *after* the gates flip — separate plan), CHANGELOG generation, end-state target ratcheting (Rust 95% / Frontend 95% — these are post-v0.1.0 monthly ratchets per `codecov.yml`'s tiered target).

## 1. Goal & Motivation

The pre-`v0.1.0` quality-gate slate exists to make the first tagged release land against gates that *enforce*, not gates that *measure*. Today three of the four bullets fall short:

- **Coverage** — `codecov.yml` uses `target: auto + threshold: 0.5%`, which is regression-prevention. A new crate added with 30% coverage won't fail the check; only a *drop* relative to the previous commit will. The end-state target is 95% line/branch (per `codecov.yml` header), but no ratchet schedule exists. The §13.7.10 Codecov-ratchet AUDIT item has been "scheduled — awaiting baseline settle" since the 22nd-pass SEED; three post-baseline ffs in as of 2026-04-23, the baseline is settled.
- **Mutation** — `ci-mutation.yml` runs ~30-60 min per target on Monday cron + `workflow_dispatch`. Each per-target job correctly checks `mutation-score.py --threshold 85` and would exit non-zero below, but the workflow has no `pull_request` trigger; PRs merge without seeing it. The 85 % threshold is also stale — three of four targets are at 100 % locally per `test-infra-followups-plan` Phase D; the gate could tighten or stay accommodating, but the choice should be deliberate.
- **§17 `list_segments_in` defensive sort** — production bug class. `compaction::merge_warm_segments` was the visible failure (`f391239`); the same `fs::read_dir`-without-sort pattern recurs across 6 other production callers (`taxonomy_parser`, `discovery`, `fs_trail`, `init.rs`, `tiered`, `fs_snapshot`). HEALTH-LOG §17 "Prevention" recommended a one-pass audit. Bundling here because it's the same shape of work — convert "happens to work on this volume" into "guaranteed to work everywhere".

The fourth item — manual keyboard-only smoke test — is operator-driven and not in this plan's scope.

The motivation *now* is that v0.1.0's release ceremony lands the first publicly-tagged binary. If gates aren't enforcing when that tag goes out, the v0.1.0 binary may not actually meet the quality bar the gates *advertise*. Worse, retroactively flipping gates after a tag means future commits get blocked on improvements the tagged binary itself shipped without — awkward and confusing for first contributors. Better: flip the gates first, ratchet to baseline, *then* tag.

If not done: the OCI publication ceremony succeeds (workflows are wired), the binaries pass the existing advisory checks, but the "Quality gates ≥ 85 %" claim in `ROADMAP.md` is aspirational rather than enforced. First external user opens an issue: "your README says 85 %, your CI doesn't check it." Fair. Better to make the README honest by making CI honest.

### 3.3 Phase P2 — Mutation gate decision + flip

**Three paths, pick one based on P0's runtime estimates:**

- **Path A — full PR-gate.** Add `pull_request: branches: [main]` to `ci-mutation.yml`. Every PR runs all 4 mutation jobs (~30–60 min × 4 = 2–4h wall). Acceptable if jobs run in parallel and tolerable for the user-driven PR cadence. Strongest gate; slowest PR turnaround.
- **Path B — cron-only with branch protection.** Add a branch-protection rule via `gh api` requiring the latest `ci-mutation.yml` run to be `success` before merge into `main`. PRs don't trigger mutation runs themselves; the operator (or a separate scheduled refresh) keeps the cron run green. Fastest PRs; requires operator discipline (cron failure becomes a merge-block).
- **Path C — split fast/slow.** PR-trigger only the fast targets (`wacp-tools/execution` is small per HEALTH-LOG §15.2 — 12 mutants, ~5 min runtime); keep slow ones (`session_monitor`, etc.) on cron. Compromise: PRs gated on the fast targets; the slow ones provide weekly health signal but don't block.

**Default recommendation:** Path C if `session_monitor` runtime > 20 min and `wacp-tools/execution` < 10 min. Path A if the slowest target is < 15 min. Path B if user explicitly prefers fastest PRs.

**Threshold question.** Three of four targets are at 100 % locally; one (`session_monitor` 98.2 %) has 1 documented-equivalent mutant. Options:
- Keep 85 % (advisory headroom for new mutants surfaced over time)
- Tighten to 90 % (still under 100 %; survives 1–2 new survivors)
- Tighten to per-target current score minus 5 pt (most aggressive; new survivors fail fast)

Recommend 90 % unless user wants per-target.

**Whichever path is chosen:** verify the gate by introducing a deliberate test deletion that allows a known-killed mutant to survive. The mutation run should fail; revert before merging.

### 3.4 Phase P3 — §17 readdir audit + sort-lift

- For each `fs::read_dir` site classified as P3-fix in P0: add `sort_by_key` or equivalent before iterating. Where the consumer iterates over results in a way that matters for output ordering (segment ids, vertical names, file paths in deterministic-output flows), the sort key should be the consumer's expected order.
- For each P3-comment site: add a brief comment above the `fs::read_dir` call explaining why order doesn't matter (e.g., "consumer aggregates into a HashMap; readdir order is irrelevant").
- Lift sort into `list_segments_in` (the original §17 follow-up) so all callers get id-sorted output by default. Per the §17 family-audit table: `transition_warm_to_cold` becomes safer-by-default (currently iterates by `seg.created`, no longer at risk if a future change switches to id-iteration).
- For any newly-fixed site, add a unit test that verifies sort-correctness — at minimum, a test that mocks readdir to return out-of-order entries and asserts the consumer sees sorted output.
- HEALTH-LOG §17 status: if all 6 remaining sites are now classified or fixed, mark the §17 follow-up resolved (strike-through the "Defensive follow-up... not landed" sentence + reference this plan).

## 5. Risks / Open Questions

### Risk #1 — Codecov baseline below proposed floor

If P0 surfaces a component (most likely `frontend` or `python`) with current coverage < 50%, flooring there isn't useful — a 30% floor doesn't enforce anything meaningful. Mitigation: for low-baseline components, set the floor at baseline-minus-5pt as a regression guard for now, plan a separate ratchet-path for that component, document the deferral in `docs/coverage-policy.md`. Don't block the plan on bringing a low-coverage component to 85% — that's a much larger separate effort.

### Risk #2 — Mutation runtime balloons under PR gate

If P0 measures `session_monitor` runtime > 30 min, Path A (full PR gate) makes PRs painful. Mitigation: default to Path C; if even the fastest target is > 15 min, fall back to Path B (branch protection on cron). The plan doesn't lock a path; P2 picks it based on data.

### Risk #3 — `fs::read_dir` audit surfaces a hot-path consumer that subtly relies on a specific order

Some readdir consumer might depend on a specific filesystem-determined order (e.g., a "newest first" assumption that happens to work because filesystems often allocate higher inodes to newer files). Adding a sort would change semantics. Mitigation: P0's per-site audit catches this; classify such a site as `no-change` with a strong comment ("DO NOT ADD SORT — consumer relies on inode-allocation-order for X reason"). If no such site exists, this risk is zero.

### Risk #4 — Test-deletion verification commits accidentally merge

P1 + P2 verification both involve deliberately-broken commits to confirm the gates fail. Easy to forget to revert before merging. Mitigation: do verification on a throwaway branch, never push to `dev` or `main`. Acceptance criteria include "verified to fail" but also "reverted before merge".

### Open Question #1 — Per-component floor or single floor?

`codecov.yml` already supports per-flag overrides (`status.project.rust-wacp:` etc). Two options for P1:
- Option A: per-component floors (rust-wacp 85, rust-console 80, frontend 60, python 70 — based on actual baselines). Most accurate; most config to maintain.
- Option B: single workspace-wide floor (e.g., 75) that all components must clear individually. Simplest; may be too low for high-coverage components.
- **Default: Option A** unless P0 shows components are within 5pt of each other.

### Open Question #2 — Block on cron failure for Path B?

If Path B is chosen and the Monday cron fails (mutation regression), `main` is now unmergeable until the regression is fixed AND the next cron runs (worst case: 7 days). Two alternatives:
- Allow `workflow_dispatch` re-runs to satisfy the gate (operator can re-fire after fix without waiting a week)
- Add a daily mini-cron in addition to the Monday full-cron
- **Default:** workflow_dispatch re-runs satisfy the gate (one-line config); decide at P2.

### Open Question #3 — Should P3 audit extend beyond `fs::read_dir`?

HEALTH-LOG §17 says "any other production code that calls `fs::read_dir` and assumes name-order is the same class of bug." But there are adjacent patterns: `glob::glob` results, `std::fs::DirEntry` collections, `Path::ancestors`. Should P3 audit them too? **Default: no** — fs::read_dir is the §17 root cause; broader audit is a separate plan if a similar bug surfaces. Document as a follow-up if any of the 6 readdir sites turn out to delegate to glob/etc.

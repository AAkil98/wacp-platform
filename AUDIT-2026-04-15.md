## 0. Scope and methodology

This audit covers the unified `wacp-platform` monorepo, which contains two formerly-separate codebases merged via `git subtree` (M0 through M7) and now integrated through a dedicated wiring phase (W1 through W7):

| Tree | Surface | Post-audit state |
|---|---|---|
| `wacp/` | Protocol runtime — 15 Rust crates, 10 TS packages, Python SDK, 7 verticals | Post Stream A (A1–A9), post-merger (M0–M7) |
| `wacp-console/` | Operator workbench — 6 Rust crates + React SPA | Post Phases 0–7, post-wiring (W1–W7) |

Methodology: two parallel thorough codebase sweeps (one per tree) followed by targeted verification of the highest-signal claims (F1 race fix, auth path, workflow inventory, YAML dep). Working tree is clean at `a6773d6`.

The wiring phase's purpose was to replace every mock or placeholder in console-core with real gRPC+REST calls against the wacp runtime. This audit verifies that was actually done.

## 1. Verdict

Both codebases are in good health and materially production-ready. Everything flagged by `AUDIT-2026-04-12.md` (the F1 test race, 8 clippy errors across `wacp-security` + `wacp-llm`, 107-file fmt drift) is resolved and CI is green. All W1–W7 wiring points are real — no `unimplemented!()`, no `Default::default()` stand-ins, no hand-rolled fixture JSON in production paths. Security posture in `wacp-console` is strong out of the gate (OWASP-compliant Argon2id, CSRF double-submit with constant-time compare, rate-limited login, 256-bit bootstrap credential written 0o600).

Three near-term items remain before a confident `v0.1.0` tag: tighten timing semantics on the runtime's auth path, add supply-chain scanning to CI (`cargo-deny`, SBOM, Trivy), and decide whether to migrate `serde_yaml_ng` → `serde_yml`. None are blocking; all are cheap.

## 6. Security

### 6.1 Runtime (wacp)

**Medium — timing-sensitive auth lookups.** `wacp/crates/wacp-transport/src/auth_api_key.rs:78–93` and `src/auth_session.rs` (analogous pattern) use `HashMap::get_mut(token)` as the primary lookup, followed by a struct-field comparison for workspace scoping. Two comments:

1. The `HashMap` lookup itself leaks timing information (bucket probes, collision chains). Rust's default hasher is `SipHash`-based, which is not intended as a constant-time primitive. Exploiting this to recover a 256-bit random token is impractical in realistic network conditions, but the pattern is not best-practice for auth tokens.
2. `&entry.identity.workspace_id != workspace_id` at `auth_api_key.rs:85` is a derived-`PartialEq` comparison on a struct that wraps a string. Non-constant-time. This only runs *after* the token matched, so it leaks whether a given workspace_id is the "right" one for a known-good token rather than leaking the token itself — lower risk than (1).

**Severity:** medium, not critical. Fix sketch: store tokens hashed (SHA-256 or better) and look up by prefix-indexed digest, or at minimum wrap the final equality in `subtle::ConstantTimeEq` once the candidate set is narrowed. The `wacp-console` auth path already uses `subtle` correctly — applying the same pattern to the runtime's in-memory token stores would be consistent.

**Informational — no secret-leaking log statements found** on either side. Spot searches for `tracing::{info,debug,warn}!(..token..)` or `println!(..password..)` returned empty.

### 6.2 Console (wacp-console)

Console security foundations are solid and match the `wcon-auth` spec promises:

| Control | Location | State |
|---|---|---|
| Argon2id (m=19456 KiB, t=2, p=1) | `crates/console-core/src/password.rs:17–20` | OWASP-compliant |
| Session cookie (`HttpOnly; Secure; SameSite=Strict`) | `crates/console-api/src/routes/auth.rs:128–148` | correct |
| CSRF double-submit (constant-time via `subtle::ConstantTimeEq`) | `crates/console-api/src/middleware.rs:100–122` | correct; bearer tokens exempt per spec |
| Login rate limit (per-IP + per-account, sliding window) | `crates/console-core/src/rate_limit.rs` + `routes/auth.rs:47–49` | wired |
| Bootstrap credential (256-bit random, printed once, file 0o600) | `crates/console-core/src/bootstrap.rs:60–85` | correct |
| API token hashing (SHA-256, constant-time compare) | `crates/console-core/src/authenticator.rs` + middleware | correct |

## 12. Testing strategy — push toward branch coverage

**Goal.** Move from line-coverage reporting (where we are) to branch-coverage reporting (where we need to be) and drive each tree toward 100% branch coverage where practical. "Where practical" excludes: `#[derive]`-generated code, `main()` wiring glue, cross-service error paths that require fault injection outside the process (covered by chaos tests instead of unit tests), and third-party proc-macro output.

Realistic per-tree targets, locked in as CI thresholds that ratchet upward only:

| Surface | Baseline (today, est.) | 90-day target | End-state |
|---|---|---|---|
| `wacp` Rust crates (non-`main`) | ~70% line, ~55% branch | 85% branch | 95% branch |
| `wacp-console` Rust crates | ~75% line, ~60% branch | 90% branch | 98% branch |
| `wacp-console` frontend (components + hooks + stores) | ~5% (smoke only) | 80% branch | 95% branch |
| TypeScript verticals (`packages/*`, `ecosystem/*`) | ~85% line | 90% branch | 95% branch |
| Python SDK | ~75% line | 85% branch | 95% branch |

Four separate pipelines (Rust, TS, Python, E2E) — each needs its own tooling, thresholds, and ratchet.

### 12.1 Tooling

| Stack | Tool | Output | CI integration |
|---|---|---|---|
| Rust (both trees) | `cargo-llvm-cov` (replaces tarpaulin — faster, branch-aware on nightly, line-accurate on stable) | `lcov.info` + HTML | Upload to Codecov; fail PR if branch % regresses > 0.5 pt |
| TypeScript (FE + packages) | Vitest `--coverage` with `@vitest/coverage-v8` | `lcov.info` | Same Codecov flow; per-package thresholds in `vitest.config.ts` |

- **`coverage.status.patch`** — new lines in the PR must be ≥ 95% covered
- **`coverage.status.project`** — project-wide branch % may not drop more than 0.5 pt
- **Component flags** — one flag per crate/package so a drop in one doesn't hide behind a rise in another

### 12.6 Mutation testing (confidence check, not gate)

Branch coverage tells us we *reached* every branch. Mutation testing tells us the tests *actually assert the right thing*. Not a PR gate — too slow, too noisy — but run weekly on:

- `wacp-transport` auth path (security-critical)
- `console-core::session_launcher` (highest-stakes console path)
- `console-core::session_monitor` (highest-concurrency console path)
- `wacp-tools::execution` (the F1 neighborhood)

Target mutation score: ≥ 85% on each. Lower scores get a weekly triage; surviving mutants either get killed by new tests or explicitly annotated as equivalent.

### 12.7 CI integration + ratchet

Per PR:
1. Each language's coverage job produces `lcov.info` / `coverage.xml`.
2. Upload to Codecov with per-component flags.
3. Codecov statuses block merge:
   - `patch/rust` ≥ 95% for new lines
   - `patch/typescript` ≥ 95% for new lines
   - `project/*` may not drop more than 0.5 pt vs. `main`
4. Nightly job runs the full matrix, posts a coverage summary to the repo's Actions tab.
5. Weekly job runs mutation testing on the four critical modules; posts a dashboard.

Thresholds start at the baseline (whatever `main` measures on day 1) and ratchet up monthly. No PR lowers the floor.

### 12.8 Anti-goals

- **Not** 100% line coverage for the sake of it. Derive blocks, trivial `impl Default`, `main()` wiring, and panic branches on infallible paths all get `#[cfg(coverage_nightly)] #[coverage(off)]` or `/* c8 ignore */` annotations with a justification comment.
- **Not** tests-for-tests'-sake. Every new test either (a) covers a previously unreached branch, (b) asserts a behavior an earlier test already reached but did not verify, or (c) documents an invariant that would otherwise live only in a spec. Redundant tests get deleted.
- **Not** slow tests in the PR path. Anything over 2s goes to the nightly matrix, not the per-PR flow.

### 13.6 New workstream: frontend test execution stability (not in original audit)

An in-flight workstream orthogonal to the §12 coverage goals: making the (now much larger) frontend Vitest suite actually runnable without crashing the developer's WSL environment. Origin: running the freshly-written F1–F9 tests under `pool: "forks"` with a 6GB `execArgv` heap ceiling caused single-worker RSS to climb past 5GB across files, killing WSL twice in-session.

Actions taken (committed in this session):

- `wacp-console/frontend/vitest.config.ts` — `execArgv` reduced from `--max-old-space-size=6144` to `--max-old-space-size=1536`. Forces V8 GC pressure early; caps any single worker so a leak OOMs vitest cleanly instead of exhausting system memory.
- `wacp-console/frontend/scripts/run-tests-isolated.sh` + `npm run test:isolated` — runs `npx vitest run <file>` once per file, each in a fresh Node process. Bounds cross-file carry-over. Trades ~30-50s walltime for a stable environment.
- The previously monolithic `src/surfaces/profiles/ProfilesPage.test.tsx` (807 lines, 48 tests) split into 5 feature-aligned files plus a `ProfilesPage.test-helpers.tsx` fixtures module.

Resolved issue exposed by the stability work (closed in `d63648a`):

- `ProfilesPage.actions.test.tsx` — diagnosis revealed this was not a memory leak but an **infinite React render loop** inside the "switches between profiles" test. The test set `mockProfile.mockImplementation` to return a fresh spread object for the "p2" branch on every call, so `useProfile`'s `.data` reference changed every render. `ProfilesPage.tsx:205`'s `useEffect([loadedProfile, creating])` therefore re-fired every render, calling `setForm`, triggering another render — unbounded. The climbing RSS was the symptom; the event loop was pinned and vitest never exited (the prior run's "340s of GC thrash" was actually 340s of React render work under a cap, not GC). Fix: swap `mockImplementation` for `mockReturnValue` (stable reference) — the assertion only checks `mockProfile` was called with `"p2"` so different-per-id data was never needed. Secondary defenses added in the same commit: module-scoped `QueryClient` + `afterEach(cleanup, queryClient.clear)` in the file, plus global `afterEach(cleanup)` in `test-setup.ts` so future test files (F7, F8, F10) don't repeat the DOM-accumulation pattern. Post-fix: `actions.test.tsx` 11/11 pass in 3.2s (peak 211 MB); full `npm run test:isolated` 16/16 pass in 54s (session peak 323 MB) — down from the prior 379s walltime and 1669 MB peak.

This workstream is not part of the §12 coverage targets and does not move the branch-coverage numbers; it is tooling to make §12 attainable in practice.

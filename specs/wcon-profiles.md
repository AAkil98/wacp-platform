## 1. Overview

A profile is the user's primary tool for expressing "how this agent should behave." It bundles a role reference, LLM configuration, autonomy preset, tool permissions, and resource budgets into a reusable, portable unit. The profile system is the Console's most user-facing backend service — every session launch requires at least one profile, and most users will spend significant time creating and tuning them.

This spec defines the behavior and rules that govern profiles. The underlying schema is defined in `wcon-data-model` §3. The taxonomy index that validates profiles is defined in `wcon-discovery`. This spec sits between those two: it defines what happens when a user creates, edits, clones, deletes, versions, imports, or exports a profile.

Three properties define the profile system:

1. **Validated** — a profile is validated against the taxonomy index at every write boundary (create, update, import). Invalid profiles are rejected with specific error messages. A profile that passes validation is guaranteed to reference a real role with real tools.
2. **Versioned** — every save creates a new version. Previous versions are retained. Sessions pin a specific version at assignment time. The user can browse version history and roll back.
3. **Portable** — profiles export to YAML and import from YAML. A profile created on one Console instance can be transferred to another. The import validates against the local taxonomy — portability does not bypass safety.
4. **Owned** — every profile belongs to the user who created it (`owner_user_id`). Visibility is `private` (owner + admins only) or `shared` (readable by all, editable by owner + admins). Authorization rules follow `wcon-auth` §4.2 and §5.

## 2. Profile Lifecycle

### 2.1 Create

A new profile is created from the profile studio editor or via the REST API.

**Authorization:** requires `operator` or `admin` console role (`wcon-auth` §4.2).

**Input:** all fields defined in `wcon-data-model` §3.1 except identity, ownership, and lifecycle fields (`id`, `version`, `owner_user_id`, `is_current`, `created_at`), which are generated by the system. Optionally includes `visibility` (defaults to `"private"`).

**Process:**

1. Validate all fields (see §3).
2. Generate a new UUID v4 for `id`.
3. Set `version = 1`, `is_current = 1`, `created_at = now()`.
4. Set `owner_user_id` to the authenticated user's `user_id`.
5. Set `visibility` to the requested value (default `"private"`).
6. Insert the row into the `profiles` table.
7. Return the complete profile with generated fields.

**API:** `POST /api/profiles`

**Success:** `201 Created` with the profile entity.

**Failure:** `422 Unprocessable Entity` with a validation error response (see §3.5).

### 2.2 Update

An existing profile is updated from the profile studio editor or via the REST API. Updates create a new version — the existing version is never mutated (`wcon-data-model` §7.2).

**Authorization:** the authenticated user must be the profile's owner or an admin. Shared profiles are editable by owner + admins, not by other operators (`wcon-auth` §5.2).

**Input:** the profile `id` plus any fields the user wants to change. Unchanged fields carry their current values — the API receives the full profile state, not a partial diff. The `visibility` field may be changed (creates a new version).

**Process:**

1. Load the current version for the given `id`. If no profile with that `id` exists, return 404. If the user lacks edit access, return 403.
2. Apply the submitted field values over the current version.
3. Validate all fields against the taxonomy index (see §3).
4. Within a transaction:
   a. Set `is_current = 0` on the existing current row.
   b. Insert a new row with the same `id`, `version = previous + 1`, `is_current = 1`, `created_at = now()`.
5. Return the new version.

**API:** `PUT /api/profiles/:id`

**Success:** `200 OK` with the new version.

**Failure:** `404 Not Found` if the profile does not exist. `422 Unprocessable Entity` if validation fails.

### 2.3 Delete

Deleting a profile is a **soft delete** — every version row for the profile's `id` has its `deleted_at` column set to the current timestamp. Rows survive so that foreign-key integrity with `session_assignments` (which pin historical `(profile_id, profile_version)` pairs) is preserved. See `wcon-data-model` §3.1 and §7.2 for the schema-level details.

**Authorization:** the authenticated user must be the profile's owner or an admin (`wcon-auth` §4.2).

**Input:** the profile `id`.

**Process:**

1. Check authorization — return 403 if the user is not the owner and not an admin.
2. Check that the profile is not assigned to any **active** session (state = `active`). If it is, reject the delete with `409 Conflict`. This is a hard block — deleting a profile whose directives are live in the runtime would leave the user looking at a "deleted" label in their oversight dashboard.
3. Within a transaction, set `deleted_at = now()` on every row for this `id`. All versions share the same `deleted_at` value (`wcon-data-model` §10.1 inv 7).
4. Check whether the profile is assigned to any **non-terminal, non-active** session (`configuring`, `validating`, or `launching`). If so, include a `warnings` array in the response listing each affected session (session ID, name, owner, state). This is informational — the delete succeeds regardless. For each affected session whose owner has an active WebSocket connection, push a `notification` channel event: `"Profile '{name}' was deleted — session '{session_name}' has an invalid assignment"`. The session owner will see the stale assignment when they open the wizard, and launch validation will reject with `DELETED_PROFILE_IN_ASSIGNMENT` until the slot is reassigned (`wcon-sessions` §3.1).
5. Historical `session_assignments` rows referencing the profile are untouched. Their FK still resolves because the parent row still exists; they continue to display the profile's name and configuration as a historical artifact.

**API:** `DELETE /api/profiles/:id`

**Success:** `200 OK` with `{ "warnings": [...] }` if any non-terminal sessions are affected. `204 No Content` if no warnings.

**Failure:** `404 Not Found` if the profile does not exist or is already deleted. `409 Conflict` if the profile is assigned to an active session.

**Undelete is not supported.** A mistakenly deleted profile is reconstructed by importing the exported YAML (or by creating a new profile with the same content). The exported YAML is the operational backup. This keeps the lifecycle simple — no "trash bin" UI, no undelete endpoint — and matches user expectations that delete is a deliberate action.

### 2.4 Hard Delete (Not Supported)

The Console never hard-deletes profile rows. All deletion is soft delete per §2.3, and the schema preserves FK integrity. If a future release requires permanent profile removal (e.g., for GDPR erasure), a separate mechanism will be introduced with explicit handling of dependent `session_assignments` — it is out of scope for this spec.

## 3. Validation

Validation runs at every write boundary: create (§2.1), update (§2.2), import (§7.3), and rollback (§5.3). Validation is synchronous and blocking — the write does not proceed until all checks pass.

### 3.1 Field-Level Validation

| Field | Rule | Error code |
|-------|------|-----------|
| `name` | Non-empty, max 200 characters, unique among the **owner's own live profiles** (`owner_user_id = ? AND is_current = 1 AND deleted_at IS NULL`); names previously used by soft-deleted profiles may be reused. Uniqueness is per-user — two different users may have profiles with the same name. Shared profiles are displayed with an owner prefix (`"{owner}'s {name}"`) so they are visually unambiguous regardless of name collisions across users (see `wcon-data-model` §3.3 `display_name`) | `INVALID_NAME` / `DUPLICATE_NAME` |
| `role_ref` | Must resolve to a role in the taxonomy index | `UNKNOWN_ROLE` |
| `llm_provider` | Non-empty string | `INVALID_PROVIDER` |
| `llm_model` | Non-empty string | `INVALID_MODEL` |
| `llm_temperature` | NULL or 0.0–2.0 | `INVALID_TEMPERATURE` |
| `llm_max_tokens` | NULL or positive integer | `INVALID_MAX_TOKENS` |
| `autonomy` | One of: `autonomous`, `assisted`, `supervised` | `INVALID_AUTONOMY` |
| `budget_warning_threshold` | 0.0–1.0 | `INVALID_THRESHOLD` |
| Budget fields | NULL or non-negative integer | `INVALID_BUDGET` |
| `tags` | Valid JSON array of strings, each tag max 50 characters | `INVALID_TAGS` |
| `visibility` | One of: `private`, `shared` | `INVALID_VISIBILITY` |

### 3.2 Tool Validation

Tool validation is the most involved check because it involves the taxonomy index and is subject to the vertical-coarse tool-role mapping defined in `wcon-discovery` §3.4.

**Vertical lookup.** Every tool reference is validated against the profile's role's vertical, not against the role itself. The profile's `role_ref` resolves to a `RoleEntry` whose `vertical` field gives the owning vertical (or `None` for base roles). Tools are then checked against that vertical's tool set.

**Allowlist validation:**

1. If `tool_allowlist` is non-NULL, parse it as a JSON array of strings.
2. For each tool ID in the array, check that the tool exists in the taxonomy index AND belongs to the same vertical as the profile's role.
3. If any tool ID fails the existence check, reject with `UNKNOWN_TOOL`.
4. If any tool ID exists but belongs to a different vertical than the role, reject with `TOOL_NOT_IN_ROLE_VERTICAL` — the tool is real but cannot be used by the role because it's scoped to a different vertical.
5. For base roles (`coordinator`, `worker`, `observer`), the vertical is `None` and no tools are available. A non-empty allowlist on a base-role profile fails with `TOOL_NOT_IN_ROLE_VERTICAL` for every entry.

**Denylist validation:**

1. If `tool_denylist` is non-NULL, parse it as a JSON array of strings.
2. Each tool ID must exist in the taxonomy index. If not, reject with `UNKNOWN_TOOL`.
3. Each tool ID that exists but belongs to a different vertical from the role emits a non-blocking warning (`TOOL_NOT_IN_ROLE_VERTICAL`) — denying a tool the role cannot use anyway is harmless.

**Effective tool set validation:**

After applying allowlist and denylist, compute the effective tool set:
- If allowlist is NULL: start with **all tools in the role's vertical** (per `wcon-discovery` §3.4 vertical-coarse mapping).
- If allowlist is non-NULL: start with the allowlist.
- Remove any tools in the denylist.

The effective set must be non-empty. A profile that disables all tools in its vertical is rejected with `EMPTY_TOOL_SET`. A base-role profile has an empty effective set by construction (base roles have no vertical tools); base-role profiles are used for coordinator workspaces and do not need an effective tool set — the `EMPTY_TOOL_SET` check is skipped when `role_ref` is a base role.

**Policy-aware tool validation (non-blocking).**

For each tool in the effective set, the validator checks `ToolEntry.policy` (`wcon-data-model` §6.1, populated from `VerticalEntry.tool_policies`, per `wcon-discovery` §3.5). Tools with a non-empty `policy` trigger a warning — not a rejection — in the validation response:

```json
{
  "warnings": [
    {
      "field": "tool_allowlist",
      "code": "TOOL_HAS_RUNTIME_POLICY",
      "message": "Tool 'trade_execute' is policy-gated at runtime: requires a prior approved compliance_check checkpoint with matching trade_id (expires after 5 minutes). The profile can still be saved; the runtime will enforce the policy at call time.",
      "value": "trade_execute",
      "policy_kind": "requires_checkpoint",
      "policy_description": "Refuses without an approved compliance_check checkpoint whose trade_id matches and that was created within the last 5 minutes."
    }
  ]
}
```

The profile editor (`wcon-ui` §5.2) uses these warnings to decorate policy-gated tools with a lock icon and tooltip. Users can save the profile with full knowledge of what the runtime will enforce.

**Why warnings, not rejections.** The Console cannot know at profile save time whether the runtime's prerequisite conditions will be met at session launch — that depends on session context, the agent's behavior, and trail state none of which exist yet. Rejecting the profile would prevent legitimate use cases (a `finance:portfolio_manager` profile with `trade_execute` is exactly the right thing to build; the compliance checkpoint is created at run time). The warning surfaces the constraint so the user can plan for it.

### 3.3 Cross-Field Validation

| Rule | Error code |
|------|-----------|
| If `autonomy` is `autonomous` AND `base_role == "worker"` AND the effective tool set contains any policy-gated or high-impact tool (see below), warn that an autonomous worker with write/execute authority should be reviewed | — (warning only) |
| Budget fields must be internally consistent: if both `budget_max_cost_micros` and `budget_max_tokens` are set, no additional cross-check is needed (they are independent limits) | — |

**Scope of the autonomous-worker warning.** The warning fires only when **all three** conditions hold:

1. The profile's `autonomy == "autonomous"`.
2. The profile's `role_ref` resolves to a role whose `base_role == "worker"`. Observer-based autonomous roles (e.g., `finance:auditor`, `health:compliance`, `analytics:validator`, `datasci:reviewer`, `devops:monitor`, `mlops:evaluator`, `swe:reviewer`) are **not** flagged — autonomous observers are the designed pattern for verticals that ship read-only background review, and the warning would be pure noise for them.
3. The effective tool set contains at least one tool that is either (a) policy-gated (`ToolEntry.policy` present) or (b) matches a known high-impact pattern (`_execute`, `_write`, `_deploy`, `_delete`, `_rotate`, `_launch`, `_submit`, etc.).

Observer-based autonomy is the common pattern introduced by the vertical expansion. When SWE was the only vertical, every vertical had exactly one autonomous role (`swe:reviewer`, an observer). The six new verticals made the autonomous-observer pattern typical — every new vertical ships at least one. A warning rule that fires for every `autonomous` profile would make the save experience noisy without improving safety. The narrowed rule targets the actual risk (an autonomous worker with write/execute authority) without flagging the legitimate pattern.

**Why the rule still exists at all.** An autonomous worker with unrestricted tools is a legitimate signal of elevated risk. The warning gives the user a chance to reconsider without blocking the save. Profiles that need this configuration — an autonomous `swe:implementer` with `code_edit` + `file_write` + `terminal` — can still be saved after the user acknowledges the warning. The rule is a reminder, not a restriction.

### 3.4 Taxonomy Dependency

Validation depends on the current state of the taxonomy index. If the taxonomy is reloaded between profile creation and profile update, a previously valid profile may become invalid (e.g., a role was removed from a vertical). This is expected and correct — the taxonomy is the source of truth for what roles and tools exist.

The profile studio provides real-time validation feedback as the user edits. The role selector dropdown is populated from the taxonomy index, so the user cannot type a freeform role ID — they select from available roles. Similarly, the tool allowlist/denylist are populated from the role's owning vertical's tool set (per `wcon-discovery` §3.4 vertical-coarse mapping, not from a per-role tool list which the upstream manifest does not provide). This makes most validation errors impossible through the UI. The API enforces the same rules for programmatic access.

### 3.5 Error Response Format

Validation errors are returned as a structured response:

```json
{
  "error": "validation_failed",
  "violations": [
    {
      "field": "role_ref",
      "code": "UNKNOWN_ROLE",
      "message": "Role 'swe:architect' does not exist in the taxonomy",
      "value": "swe:architect"
    },
    {
      "field": "tool_allowlist[2]",
      "code": "TOOL_NOT_IN_ROLE_VERTICAL",
      "message": "Tool 'trade_execute' belongs to the Finance vertical; the profile's role 'swe:implementer' belongs to the SWE vertical. Tools are vertical-scoped (`wcon-discovery` §3.4).",
      "value": "trade_execute",
      "tool_vertical": "finance",
      "role_vertical": "swe"
    }
  ],
  "warnings": [
    {
      "field": "tool_allowlist[1]",
      "code": "TOOL_HAS_RUNTIME_POLICY",
      "message": "Tool 'compliance_check' is policy-gated at runtime: requires a prior approved compliance_check checkpoint with matching trade_id (expires after 5 minutes). The profile can still be saved; the runtime will enforce the policy at call time.",
      "value": "compliance_check",
      "policy_kind": "requires_checkpoint",
      "policy_description": "Refuses without an approved compliance_check checkpoint whose trade_id matches and that was created within the last 5 minutes."
    },
    {
      "field": "tool_denylist[0]",
      "code": "TOOL_NOT_IN_ROLE_VERTICAL",
      "message": "Tool 'deploy_execute' belongs to the DevOps vertical — denying it from an SWE profile has no effect",
      "value": "deploy_execute"
    }
  ]
}
```

Multiple violations and warnings can be returned in a single response. The backend validates all fields before returning, rather than stopping at the first error. **Violations** block the save (the profile is not written); **warnings** do not block the save (the profile is written and the warnings are attached to the response for the client to surface).

## 4. Profile-to-WACP Mapping

When a profile is used in a session, the Console translates it into WACP runtime constructs. The profile is the user's abstraction; the runtime understands workspaces, directives, and agent configurations.

### 4.1 Mapping Table

| Profile field | WACP construct | Delivered via |
|---------------|---------------|---------------|
| `role_ref` | Workspace role binding | `CoordinatorService.Dispatch` gRPC call — role field (`wcon-sessions` §4.2) |
| `llm_provider` + `llm_model` | Agent LLM configuration | Directive envelope payload — `llm` section |
| `llm_temperature` | LLM parameter | Directive envelope payload — `llm.temperature` |
| `llm_max_tokens` | LLM parameter | Directive envelope payload — `llm.max_tokens` |
| `autonomy` | Gate policy | Workflow gate configuration — autonomy level determines which gates activate |
| `tool_allowlist` / `tool_denylist` | Agent tool whitelist | Directive envelope payload — `tools` section (effective tool set after allow/deny) |
| `budget_*` fields | Workspace resource budget | `CoordinatorService.Dispatch` gRPC call — `ResourceBudget` message |
| `name` | Workspace metadata annotation | Trail annotation — human-readable label for the workspace (enriched by `wcon-highway` §7) |
| `description` | — | Not sent to runtime; Console-only metadata |
| `tags` | — | Not sent to runtime; Console-only metadata |

### 4.2 Directive Payload Structure

The Console constructs a directive envelope for each worker workspace. The directive payload includes the profile's operational fields plus the session's vertical context:

```json
{
  "task": {
    "id": "task-uuid",
    "description": "Task description from workflow stage"
  },
  "llm": {
    "provider": "anthropic",
    "model": "claude-sonnet-4-20250514",
    "temperature": 0.3,
    "max_tokens": 8192
  },
  "tools": ["market_data_fetch", "compliance_check", "trade_execute"],
  "system_prompt": "You are a portfolio management agent...",
  "context": {
    "compliance_scope": "equities",
    "jurisdiction": "SEC"
  }
}
```

| Field | Source | Notes |
|-------|--------|-------|
| `task` | Workflow stage | Stage description and identifier |
| `llm` | Profile | Operational LLM configuration |
| `tools` | Profile | Effective tool set after allowlist/denylist |
| `system_prompt` | Vertical default profile (`wcon-discovery` §2.2.2 `ProfileSummary` when present) | Behavioral instructions shipped with the vertical; omitted when absent |
| `context` | Session | Pass-through of `session.context` from `wcon-sessions` §2.1 step 4 / `wcon-data-model` §4.1 |

**About the `context` field.** This is a direct pass-through of the session's vertical context map. The Console does not inspect or transform the values — they are delivered to the agent verbatim. The agent may read the context to understand its operating environment (e.g., a DevOps agent reads `environment=production` and adjusts its behavior). The runtime may also read the context to enforce tool-layer policies (`wcon-discovery` §2.2.2 `ToolPolicy` kinds `requires_gate` and `budget_limited` typically read context fields).

The `context` field is absent (rather than `{}` or `null`) for sessions whose vertical has an empty `context_schema`. Absent `context` is semantically different from `context: {}` — an agent checking for a specific field should fail gracefully on absent, not on missing.

**The Console does not read vertical-specific fields it does not understand.** If the context map contains a field the Console's local projection of `context_schema` does not include (e.g., after a runtime upgrade that added a new field), the Console still passes it through unchanged. Forward compatibility is preserved by opacity (`wcon-discovery` §2.2.3).

The `system_prompt` field comes from the vertical's default agent profile for the role (`ProfileSummary`), not from the Console profile. The Console profile configures operational parameters; the vertical defines behavioral instructions. If no default agent profile exists for the role, the system prompt is omitted and the runtime uses its own default.

### 4.3 Budget Mapping

Profile budget fields map directly to WACP's `ResourceBudget` message:

| Profile field | ResourceBudget field |
|--------------|---------------------|
| `budget_max_cost_micros` | `max_cost_micros` |
| `budget_max_tokens` | `max_tokens` |
| `budget_max_wall_time_ms` | `max_wall_time_ms` |
| `budget_warning_threshold` | `warning_threshold` |

NULL profile budget fields result in no limit being set on the corresponding `ResourceBudget` field — the runtime applies its own defaults.

Session-level and assignment-level budget overrides (`wcon-data-model` §4) take precedence over profile defaults. The final budget sent to the runtime is the most specific non-NULL value in the chain: assignment override → session override → profile default → no limit.

**MLOps compute budget is not part of `ResourceBudget`.** MLOps verticals use a `compute_budget` context field (typically GPU-hours) enforced by the `train_launch` tool's `budget_limited` policy (`wcon-discovery` §2.2.2). This is **not** a Console-enforced resource limit — it is a vertical-specific metric that flows through session context (`wcon-sessions` §2.1 step 4) rather than the `ResourceBudget` chain. The profile editor does not expose a "max GPU-hours" field because such a field would be per-session, not per-profile — the same MLOps training profile is reusable across sessions with different compute budgets.

The general rule: `ResourceBudget` fields are the three dimensions WACP enforces at the workspace level (cost/tokens/wall-time). Anything else a vertical wants to budget against (compute, quota, concurrency, rate) flows through context and is enforced at the tool layer.

## 5. Version Management

### 5.1 Version History

Each profile maintains a linear version history. The user can browse the history to see what changed between versions. Soft-deleted profiles return `404 Not Found` from this endpoint — version history is only surfaced for live profiles. Session detail views (`wcon-sessions` §9.4) can still render individual historical versions of deleted profiles by looking up the pinned `(profile_id, profile_version)` directly.

**API:** `GET /api/profiles/:id/versions`

**Response:**

```json
{
  "profile_id": "uuid",
  "current_version": 5,
  "versions": [
    {
      "version": 5,
      "is_current": true,
      "created_at": "2026-04-09T14:30:00Z",
      "summary": { "role_ref": "swe:implementer", "llm_model": "claude-sonnet-4-20250514", "autonomy": "assisted" }
    },
    {
      "version": 4,
      "is_current": false,
      "created_at": "2026-04-08T10:15:00Z",
      "summary": { "role_ref": "swe:implementer", "llm_model": "claude-sonnet-4-20250514", "autonomy": "autonomous" }
    }
  ]
}
```

The `summary` field contains a subset of fields for quick comparison without loading the full version.

### 5.2 Version Detail

**API:** `GET /api/profiles/:id/versions/:version`

Returns the full profile state for that version, identical to the current version response format.

### 5.3 Rollback

Rolling back to a previous version creates a new version with the old version's field values (`wcon-data-model` §7.2). The version history remains append-only — rollback does not delete or rewrite history.

**API:** `POST /api/profiles/:id/rollback`

**Input:**

```json
{
  "target_version": 3
}
```

**Process:**

1. Load the target version. If it does not exist, return 404. If the profile is soft-deleted (`deleted_at IS NOT NULL`), return 404 — deleted profiles cannot be rolled back. (Undelete is not supported — see §2.3.)
2. Copy all field values from the target version, **excluding** `id`, `version`, `is_current`, `created_at`, and `deleted_at`.
3. Validate the copied fields against the current taxonomy index. If validation fails (e.g., the role no longer exists, a tool is now in a different vertical), return 422 with the validation error.
4. Create a new version using the standard update process (§2.2).
5. Return the new version.

Rollback can fail if the taxonomy has changed since the target version was created. This is intentional — the taxonomy is the source of truth. The user must fix any invalid references before the rollback can proceed.

Rollback does **not** resurrect any prior `TOOL_HAS_RUNTIME_POLICY` warnings verbatim — warnings are recomputed against the current taxonomy, so a rolled-back profile may surface different warnings than the original target version emitted. This is correct: the purpose of warnings is to describe current runtime enforcement, not historical state.

### 5.4 Session Pinning

When a profile is assigned to a session, the assignment records the exact `(profile_id, profile_version)` pair (`wcon-data-model` §4.2). This means:

- Editing a profile after assigning it to a session does not change the session's configuration.
- The session launcher shows the pinned version, not the current version, in the session detail view.
- If the user wants a session to use an updated profile, they must reassign it (only possible while the session is in `configuring` state).

## 6. Clone

Cloning creates a new profile with copied field values but a new identity.

**API:** `POST /api/profiles/:id/clone`

**Input (optional):**

```json
{
  "name": "Fast Implementer (copy)"
}
```

**Authorization:** requires `operator` or `admin` console role. The user must have read access to the source profile (own profile, shared profile, or admin).

**Process:**

1. Load the current version of the source profile. If the user lacks read access, return 403.
2. Generate a new UUID v4 for the clone's `id`.
3. Set `version = 1`, `is_current = 1`, `created_at = now()`.
4. Set `owner_user_id` to the authenticated user (the cloner, not the source owner). Set `visibility = "private"`.
5. Copy all field values from the source (role_ref, LLM config, autonomy, tools, budget, tags).
6. If a `name` is provided in the input, use it. Otherwise, append `" (copy)"` to the source profile's name. If the resulting name conflicts with an existing profile, append a numeric suffix (`" (copy 2)"`, etc.).
7. Set `description` to the source's description.
8. Validate the cloned profile against the taxonomy (same rules as create).
9. Insert the row.
10. Return the new profile.

The clone has no relationship to the source profile — it is an independent entity with its own version history. The clone's version 1 is not linked to the source's version history.

## 7. Import/Export Workflow

### 7.1 Export

Export serializes a profile to a YAML file following the format defined in `wcon-data-model` §8.1.

**API:** `GET /api/profiles/:id/export`

**Process:**

1. Load the current version of the profile.
2. Serialize to the YAML format, omitting internal fields (`id`, `version`, `is_current`, `created_at`).
3. Omit NULL optional fields.
4. Return the YAML as a downloadable file with `Content-Type: application/x-yaml` and `Content-Disposition: attachment; filename="<profile-name>.yaml"`.

**Frontend behavior:** the export button in the profile studio triggers a file download. No intermediate dialog — the file downloads immediately.

### 7.2 Export Specific Version

**API:** `GET /api/profiles/:id/versions/:version/export`

Same process as §7.1 but loads the specified version instead of the current version. This allows exporting a historical version for sharing or backup.

### 7.3 Import

Import parses a YAML file and creates a new profile, following the rules in `wcon-data-model` §8.3.

**API:** `POST /api/profiles/import`

**Authorization:** requires `operator` or `admin` console role.

**Input:** multipart form upload with a single YAML file.

**Process:**

1. Parse the YAML file. If parsing fails, return `400 Bad Request` with parse error details.
2. Extract profile fields from the YAML structure.
3. Map YAML fields to schema fields:
   - `profile.role` → `role_ref`
   - `profile.llm.provider` → `llm_provider`
   - `profile.llm.model` → `llm_model`
   - `profile.llm.temperature` → `llm_temperature` (NULL if absent)
   - `profile.llm.max_tokens` → `llm_max_tokens` (NULL if absent)
   - `profile.autonomy` → `autonomy` (default `"assisted"` if absent)
   - `profile.tools.allow` → `tool_allowlist` (NULL if absent)
   - `profile.tools.deny` → `tool_denylist` (NULL if absent)
   - `profile.budget.*` → budget fields (NULL if absent)
   - `profile.name` → `name`
   - `profile.description` → `description`
   - `profile.tags` → `tags`
4. Generate a new UUID v4 for `id`. Set `version = 1`. Set `owner_user_id` to the authenticated user. Set `visibility = "private"`.
5. Validate all fields against the taxonomy index (§3). If the response contains any **violations**, return `422 Unprocessable Entity` with the validation error and the parsed field values (so the UI can show the imported data with errors highlighted). If the response contains only **warnings** (`TOOL_HAS_RUNTIME_POLICY`, autonomous-worker warning, `TOOL_NOT_IN_ROLE_VERTICAL` on denylist), the import proceeds — warnings do not block the save.
6. Check name uniqueness against the **importing user's own live** profiles only (`owner_user_id = importing_user AND deleted_at IS NULL`). A name previously used by a soft-deleted profile can be reused. If the name conflicts with one of the importer's own live profiles, the import fails with `DUPLICATE_NAME` — the user must rename. Another user having a profile with the same name does not block import.
7. Insert the row.
8. Return the new profile, with any non-blocking warnings attached to the response body so the UI can surface them in the imported profile's detail view (`wcon-ui` §5.4).

**Frontend behavior:** the import button opens a file picker. After selecting a file, the profile studio shows a preview of the imported profile with validation status. If valid (no violations), the user confirms to save, and any warnings are shown as inline notices in the detail view afterwards. If invalid (one or more violations), the validation errors are shown inline in the editor and the user can edit the fields before saving.

### 7.4 Round-Trip Fidelity

Export followed by import on the same Console instance (with the same taxonomy) produces a functionally identical profile. The only differences are `id` (new UUID), `version` (reset to 1), and `created_at` (current time). All operational fields are preserved.

Export followed by import on a different Console instance may fail if the target instance has a different taxonomy (missing roles or tools). This is expected — the import's validation against the local taxonomy catches these mismatches.

## 8. Profile Library Operations

### 8.1 List

**API:** `GET /api/profiles`

Returns the current version of live profiles visible to the authenticated user:
- **Admins** see all live profiles (any owner, any visibility).
- **Operators** see own profiles (any visibility) + other users' shared profiles.
- **Viewers** see own profiles (any visibility) + other users' shared profiles.

The underlying query is: `is_current = 1 AND deleted_at IS NULL AND (owner_user_id = :me OR visibility = 'shared' OR :role = 'admin')`. Soft-deleted profiles are filtered out. Historical session detail views (`wcon-sessions` §9.4) can still resolve deleted profiles by `(profile_id, profile_version)` directly, bypassing this list endpoint.

**Query parameters:**

| Parameter | Type | Description |
|-----------|------|-------------|
| `role_ref` | string | Filter by role reference |
| `vertical` | string | Filter by the vertical that defines the profile's role |
| `tag` | string | Filter by tag (profiles containing this tag) |
| `q` | string | Search by name or description (case-insensitive substring) |
| `sort` | string | Sort field: `name` (default), `created_at`, `role_ref` |
| `order` | string | Sort order: `asc` (default), `desc` |
| `limit` | integer | Max items per page (default 50, cap 200) |
| `cursor` | string | Pagination cursor |

**Response:** paginated list of profile summaries:

```json
{
  "items": [
    {
      "id": "uuid",
      "version": 5,
      "name": "Fast Implementer",
      "description": "High-autonomy implementer",
      "role_ref": "swe:implementer",
      "role_name": "Implementer",
      "autonomy": "autonomous",
      "llm_provider": "anthropic",
      "llm_model": "claude-sonnet-4-20250514",
      "tags": ["swe", "fast"],
      "owner_user_id": "uuid",
      "owner_username": "jane",
      "visibility": "shared",
      "created_at": "2026-04-09T14:30:00Z",
      "is_valid": true
    }
  ],
  "cursor": "...",
  "has_more": false
}
```

The `is_valid` field is computed at query time by checking whether the profile's `role_ref` still resolves in the taxonomy index AND every tool ID in the `tool_allowlist` / `tool_denylist` still exists AND still belongs to the same vertical as the role (per `wcon-discovery` §3.4). This avoids a full validation pass — it checks only existence and vertical scope, not all field rules. Profiles with new `TOOL_HAS_RUNTIME_POLICY` warnings are still `is_valid = true` because warnings are non-blocking.

### 8.2 Get

**API:** `GET /api/profiles/:id`

Returns the current version of a single profile with all fields, plus derived fields (`wcon-data-model` §3.3):

- `role_name` — resolved from taxonomy index
- `available_tools` — the effective tool set after applying allowlist/denylist against the role's tools
- `version_count` — total number of versions

### 8.3 Bulk Operations

The profile library supports two bulk operations for library management:

**Bulk delete:** `POST /api/profiles/bulk-delete`

```json
{
  "ids": ["uuid-1", "uuid-2", "uuid-3"]
}
```

Each profile is validated individually (not assigned to active sessions). The response reports success and failure per ID:

```json
{
  "deleted": ["uuid-1", "uuid-3"],
  "failed": [
    { "id": "uuid-2", "reason": "assigned to active session 'abc'" }
  ]
}
```

**Bulk export:** `POST /api/profiles/bulk-export`

```json
{
  "ids": ["uuid-1", "uuid-2"]
}
```

Returns a ZIP archive containing one YAML file per profile, named `<profile-name>.yaml`.

## 9. Invariants

These rules extend the profile invariants defined in `wcon-data-model` §10.1 with behavioral guarantees.

### 9.1 Validation Completeness

Every profile stored in the database passed full validation (§3) at the time of its creation or most recent update. No profile enters the database without validation.

### 9.2 Version Monotonicity

Version numbers for a given profile ID are strictly increasing with no gaps. Version N+1 is always the immediate successor of version N. Rollback creates a new version at the head, not a branch.

### 9.3 Taxonomy Authority

The taxonomy index is the sole authority for role and tool validity. The profile system does not maintain its own list of valid roles or tools. If the taxonomy says a role exists, the profile system accepts it. If the taxonomy says a role does not exist, the profile system rejects it.

### 9.4 No Implicit Mutation

Editing a profile never changes its `id`. Cloning a profile never inherits the source's `id`. Importing a profile never reuses an existing `id`. Rollback never modifies existing version rows. Every write operation that produces a profile row either creates a new `id` (create, clone, import) or appends a new version to an existing `id` (update, rollback).

### 9.5 Session Isolation

A profile update, deletion, or rollback never affects the configuration of any existing session assignment. Session assignments pin `(profile_id, profile_version)` and the pinned row is write-once for every operational field. The profile system and the session system interact only at the moment of assignment.

Soft-deletion is the one narrow exception: `deleted_at` is mutated on existing rows when the user deletes a profile. This does not affect session assignments because (a) the FK still resolves (the row still exists), (b) the session monitor reads the pinned version's field values, not `deleted_at`, and (c) the historical session detail view shows the profile's name and configuration regardless of its `deleted_at` state. Session fidelity is unchanged by soft delete.

### 9.6 Import Parity

An imported profile is subject to exactly the same validation rules as a manually created profile. The import path does not bypass, relax, or defer any validation. If a profile cannot be created through the UI with those field values, it cannot be imported from YAML either.

### 9.7 Ownership Immutability

A profile's `owner_user_id` is set at creation (§2.1), clone (§6), or import (§7.3) and never changes. All versions of a profile share the same `owner_user_id` (`wcon-data-model` §10.1 inv 8). Transfer of ownership is not supported.

### 9.8 Authorization at Every Boundary

Every write operation (create, update, delete, clone, import, rollback, bulk-delete) checks the authenticated user's console role and ownership before proceeding. The frontend hides unauthorized affordances as a convenience, but the backend enforces access independently (`wcon-auth` §4.3).

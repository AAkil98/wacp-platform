# v0.1.0 readiness — a11y + spec-drift + backend perf baseline

> **Triggering findings:** HEALTH-LOG §2.5 (3 frontend components drifted from AUDIT deliverables), §4 P4 residual (20 `<div onClick>` keyboard-nav warnings from F8), §8 (backend perf unsurveyed), §10.1/10.2 (wacp-llm stub allocation opts), §9.3 (console-db migration cost note).
> **Goal:** close the three remaining v0.1.0-readiness clusters — a11y keyboard-nav, spec-vs-impl drift, and backend perf baseline — as one coherent pre-tag sweep.
> **Target branch:** `refactor/v0.1.0-readiness` from `dev` (post-2026-04-20 ff at `1b48ff8`). Three tracks (A/B/C), 13 phases total. ff to dev at end.
> **Rough effort:** ~10–16 h. Track A (~2–3 h) → Track B (~3–5 h) → Track C (~5–8 h). Sequential; each track exits green before the next starts.
> **Not in scope:** `integration/port-allocation-toctou` (§14.1 — standalone plan; requires `--listen-fd` CLI work in wacp-runtime first); `recovery/closed-terminal-coverage` (§11.4 footnote — single-commit follow-up); `ci/codecov-ratchet` + `ci/playwright-coverage-merge` (standalone CI hygiene); §13.7.8 deferred sub-scenarios (infrastructure-blocked).

## 1. Goal & Motivation

With every AUDIT §13.7 package + closeout-plan + bucket-B refactor + frontend-perf-plan closed on `main` at `1b48ff8`, the three clusters below are what remains between the current state and a v0.1.0 tag.

**Track A** closes the direct residual from F8 (the keyboard-nav warnings held at `warn` so F8 could ship without a same-PR keyboard-nav sweep). Flipping them back to `error` is the end-state the §4 P4 doc describes.

**Track B** closes three AUDIT §13.7.4 drifts that have been in §2.5 since 2026-04-15, unchanged. Each is a Yes/No decision the spec can't defer through a tag cut: does the feature ship, or does the spec harmonize down? `Notifications` is the most severe (a component that compiles but is never imported and has no data flowing into it).

**Track C** establishes numerical baselines for three hot paths before they become post-v0.1.0 regression candidates. HEALTH-LOG §8 has been explicit since initial authoring that the backend side has not produced runtime-perf signals in any session — which means we also have no tripwires. Shipping without baselines means the first post-v0.1.0 perf regression has no reference point to compare against.

**If not done:** v0.1.0 ships with 20 keyboard-inaccessible interactive surfaces (legal / compliance risk if the product claims WCAG AA), three AUDIT-documented features that don't exist in the running product (support-facing risk — operators will ask for the missing toast-notification flow), and no `cargo bench` baselines to catch the first post-tag perf regression.

## 3. Deliverables — per phase

### 3.1 Track A — A11y keyboard-nav sweep

**Source:** HEALTH-LOG §4 P4 residual from F8 commit `8761117`. 20 violations across 8 files, all the `jsx-a11y/click-events-have-key-events` + `jsx-a11y/no-static-element-interactions` pair.

**A1 — shared wrapper.** Create `wacp-console/frontend/src/components/ClickCard.tsx`:

```tsx
import type React from "react";
import { useCallback, type KeyboardEvent } from "react";

interface ClickCardProps extends React.HTMLAttributes<HTMLDivElement> {
  onClick: () => void;
}

export function ClickCard({ onClick, children, ...rest }: ClickCardProps) {
  const onKeyDown = useCallback(
    (e: KeyboardEvent<HTMLDivElement>) => {
      if (e.key === "Enter" || e.key === " ") {
        e.preventDefault();
        onClick();
      }
    },
    [onClick],
  );
  return (
    <div role="button" tabIndex={0} onClick={onClick} onKeyDown={onKeyDown} {...rest}>
      {children}
    </div>
  );
}
```

**A2 — apply to 8 sites.** Straight swap `<div onClick=...>` → `<ClickCard onClick=...>` keeping style / children unchanged. For the two auth-page overlays (LoginPage, ChangePasswordPage) which are modal backgrounds, use a different pattern: move the `onClick={close}` to a `<button>` with `aria-label="Close dialog"` positioned `absolute` and visually hidden, and add `onKeyDown` listening for `Escape` on the overlay. For the Notifications row, use a real `<button>` since it's a proper interactive element, not a card.

**A3 — rule flip.** In `eslint.config.js`, change both rules from `warn` to `error` and delete the follow-up rationale comment since the work landed. Verify `pnpm lint` exits 0.

**Test impact.** RTL tests that currently do `fireEvent.click(screen.getByText("...label..."))` still work — `ClickCard` passes through the click handler and preserves the child content. Tests may prefer the semantic `getByRole("button", { name: /label/i })` going forward; update opportunistically, not required.

**Commit strategy:** one commit per logical unit — A1 scaffold, A2 (single atomic commit across 8 sites since it's mechanical), A3 rule flip. 3 commits.

### 3.3 Track C — Backend perf baseline

**Source:** HEALTH-LOG §8 (general), §10.1/10.2 (stub-specific), §9.3 (console-db migration).

**C1 — bench harness scaffold.**

Add `criterion = { version = "0.5", default-features = false, features = ["html_reports"] }` to `[dev-dependencies]` in three `Cargo.toml`s:
- `wacp-console/crates/console-core/Cargo.toml`
- `wacp-console/crates/console-api/Cargo.toml`
- `wacp/crates/wacp-llm/Cargo.toml`

Create `benches/` directory in each with a single `bench.rs` using `criterion::criterion_group!` + `criterion::criterion_main!`. Wire `[[bench]]` entries in the Cargo.tomls.

Top-level `scripts/bench-baseline.sh` runs all three + emits a summary at `docs/perf-baseline-2026-04-20.md`.

**Not in CI.** Bench wallclocks are too noisy for CI-grade alerting without dedicated hardware. Add a README note to that effect.

**C2 — `session_monitor` broadcast fan-out.** The hot path today: `SessionMonitorHandle::broadcast_tx.send(frame)` → N subscribers. Bench spawns N=16 subscribers + pushes M=1000 frames, measures end-to-end latency per frame (publish → receive). Output: p50 / p95 / p99. Baseline target: p99 < 1 ms at 16/1000 on dev box.

**C3 — `session_launcher` coordinator sequence.** `SubmitGoal → Decompose(N) → Dispatch(N)` against a mock coordinator (reuse `InjectableCoordinator` from §13.7.8). Bench at N=1, 4, 16, 64 tasks. Output: walltime per phase + total. Baseline target: total < 50 ms at N=64 on dev box. Anomaly: non-O(N) scaling.

**C4 — `console-api/middleware` auth + CSRF.** Per-request overhead: Argon2id password verify (bypassed for bearer/cookie — so this bench specifically times the Argon2id + PHC path that triggers on `/api/login`), CSRF double-submit compare, rate-limit bucket lookup. Baseline: Argon2id < 100 ms (cost-factor-calibrated), CSRF + rate-limit combined < 1 ms.

**C5 — `wacp-llm` stub single-call serialization** (§10.1). Lift `serialize_for_match(messages, tools)` to the caller; pass `(serialized, len)` into `resolve_response()`. Bench: `complete()` walltime before + after on a 500-char fixture. Expected delta: ~20% of `complete()` walltime recovered per call.

**C6 — `wacp-llm` stub lazy streaming** (§10.2). Replace `futures::stream::iter(events).then(delay)` with `async_stream! { for event in resolve_stream() { yield event; delay.await; } }`. Bench: RSS peak during `complete_stream()` on 1000-event fixture. Expected: peak drops from O(events) to O(1 event).

**C7 — `console-db` migration amortization revisit** (§9.3). Measure current `create_test_pool()` walltime. If >10 ms mean, scaffold the `lazy_static!` migrated-template + `ATTACH DATABASE` optimization; otherwise record the measurement and move on.

**Commit strategy:** C1 standalone; C2/C3/C4 one commit each (three bench files); C5+C6 one commit (paired opt); C7 either one commit (act) or a docs-only commit (measure + decide skip). 5–6 commits total.

## 5. Risks / Open Questions

- **A2 scope creep.** The 8 sites are well-defined, but the two auth-page overlays (LoginPage, ChangePasswordPage) are actually modal dialogs, not cards — they need different treatment (`Escape` key listener + focus trap, not Enter/Space). If the fix becomes a dialog-a11y audit, scope-cut to `<div onClick>` → `<ClickCard>` for the 6 card/row sites and file the two dialogs as a separate `dialog-a11y` follow-up.
- **B1 decision.** The "wire" path requires backend work (`notification` channel event shape on highway) that may not be pre-specified. If the shape isn't specified, delete; file a `notifications/wire` plan post-v0.1.0 with the channel shape as its own deliverable.
- **B2/B3 decision.** Both hinge on a reading of `wcon-highway` + `wcon-ui` intent. If the spec is ambiguous, the default is harmonize-down (ship what exists, rewrite AUDIT) — feature additions post-tag are cheaper than feature retractions.
- **C1 harness choice.** `criterion` is the Rust standard but has nontrivial setup overhead. Alternative: `divan` (simpler, faster iteration). Defaulting to `criterion` for ecosystem familiarity; flip if the harness work balloons.
- **C4 Argon2id cost factor.** If C4 reveals the Argon2id verify path is substantially slower than expected (e.g., >500 ms p99), that's a *security* finding (cost-factor too high for login UX) — file as a §15 in HEALTH-LOG and escalate before tagging.
- **C6 `async_stream!` vs current iter-then.** The `async_stream!` macro requires the `async-stream` crate. Verify license compatibility (MIT — OK under `deny.toml`) before committing.
- **Branch sprawl.** 13 phases × ~1 commit each = ~13 commits on one branch. Cut to 2 sibling branches (`refactor/v0.1.0-frontend` + `refactor/v0.1.0-backend`) only if review-bandwidth needs it; default single branch `refactor/v0.1.0-readiness`.

## 8. Sequencing notes

**Preferred order:** A1 → A2 → A3 → B1 → B2 → B3 → C1 → C2 → C3 → C4 → C5 → C6 → C7 → closeout.

- **A before B.** A is low-surface (wrapper + 8 swaps); lands a visible a11y win fast and clears the F8 residual.
- **B before C.** B is decision-heavy and user-facing; C is mechanical but requires C1's harness landed first.
- **C1 gates C2–C7.** Every bench needs the harness. If C1 takes >2 h, scope-cut: drop C7 (it's a measure-only phase) and C6 (fold into post-v0.1.0) first.
- **B decisions can surface scope expansions.** If B1 goes the "wire" route, it might trigger a backend-channel-shape decision that exceeds Track B's 5 h budget. Budget hold at 6 h — above that, cut to "delete for v0.1.0, file follow-up."

**Alternative parallel ordering (multi-session):**
- Session 1 (~3 h): Track A complete + B1.
- Session 2 (~3 h): B2 + B3 + HEALTH-LOG propagation.
- Session 3 (~4 h): C1 + C2 + C3 + C4 (the four benches that matter most for v0.1.0).
- Session 4 (~3 h): C5 + C6 + C7 + plan close.

**Cut points.** The plan is designed to ship at any of these boundaries:
1. After Track A only — ships the F8 residual, leaves B/C as separate plans.
2. After Track A + B — ships all user-facing readiness; C becomes post-v0.1.0.
3. Full plan — pre-v0.1.0 readiness complete.

**Actual outcome 2026-04-20:** held at cut-point #2. Tracks A + B landed in a single branch (`refactor/v0.1.0-readiness`, 5 commits `f0527d7..d87b085`). Track C's 7 phases (~5–8 h of bench-writing) require a dedicated session — carved to `impl/backend-perf-baseline-plan.md` so the v0.1.0-readiness work ships without waiting on it. This plan stays `status: draft` with Track C phases marked "deferred"; archive when the successor plan lands.

# Tech-debt baseline + triage — 2026-04-18

> Data-first survey of code volume, file complexity, build artifacts, and dep footprint across the `wacp-platform` monorepo. Written after §11.4 surfaced a copy-paste-bug pattern directly caused by a 2200-line production file. Purpose: ground pre-launch and post-v0.1 decisions in numbers rather than vibes, and carry the findings forward into future sessions as the plan of record.

## 1. Headline

The user-facing footprint is **not the problem**. Binary sizes, SPA bundle, and OCI image estimates are all in normal ranges for a Rust-Tonic + Axum + React stack. The problem is **contributor-facing**: eleven production source files over 1500 lines each, a legacy subtree still wired into CI, and one build-config choice that leaks a sourcemap into the release binary. The survey separates those into three buckets:

- **A. Pre-launch deletion** (low risk, visible wins, safe this week).
- **B. Post-v0.1 structural refactor** (high cost, clear payoff, do once on a dedicated branch).
- **C. Prevention** (cheap CI guardrails so the problem doesn't compound).

The anti-pattern this doc exists to prevent: treating A and B as one emergency and rippling changes across the tree mid-merge while dev is 34 commits ahead of main.

## 3. Classification

### 3.1 Bucket A — Pre-launch, pure deletion

**A.1 — Vite sourcemap in prod build.** `wacp-console/frontend/vite.config.ts:24` sets `sourcemap: true`. `rust-embed` includes the entire `dist/` into the release binary (`assets.rs:24: #[folder = "$CARGO_MANIFEST_DIR/../../frontend/dist/"]`). Result: the 1.7 MB `.js.map` ships inside every release binary and every OCI image, and is served to any client that requests `/assets/index-*.js.map` via `serve_embedded` (mime set to `application/json` at `assets.rs:78`). Two problems: ~1.7 MB of pointless binary weight, and a prod info-leak (sourcemaps don't contain secrets, but they reveal original source structure including file paths and un-minified identifiers).

- **Effort:** 2 min edit + rebuild.
- **Fix:** change to `sourcemap: "hidden"` (keeps maps in dist for local debug, doesn't reference them from the `.js` output) or `sourcemap: false` (simplest).
- **Risk:** zero.
- **Payoff:** -1.7 MB per binary, -1.7 MB per OCI image, one info-leak closed.

**A.2 — `wacp/highway-ui/` legacy subtree. User decision required.**

Facts:
- Separate React + Vite + buf-generate app (66 files, 8,592 TS/TSX lines plus 1,876 generated).
- `wacp/impl/highway-ui.md` is a `complete` status impl spec from 2026-03-20 (before the console existed).
- SEED.md describes it as "legacy highway webapp".
- Has its own CI stage (`ci-wacp.yml:81–97 "TypeScript — highway-ui"`).
- Has its own `package.json`, `pnpm-lock.yaml`, `vite.config.ts`, `buf.gen.yaml`.
- Is **not** referenced by either Dockerfile — doesn't ship to users.
- Is **not** referenced by any runtime code.
- Its function (human highway gate/escalation/envelope UI) is now subsumed by the console's oversight dashboard (W4).

If it's truly superseded (the user's call — I shouldn't delete this unilaterally), removing it eliminates:
- 8,592 lines of source
- 1,876 lines of generated proto bindings
- 269 MB of node_modules from the dev environment
- 2.5 MB of dist output
- Its own CI stage (faster overall CI)
- Its own eslint/vitest/tsc toolchain from the contributor mental model
- The impl spec `wacp/impl/highway-ui.md`
- 19 file references across SEED.md, AUDIT, README, impl docs

- **Effort:** 10 min with `git rm -r` + CI workflow edit + doc grep sweep.
- **Risk:** irreversible at the branch level (recoverable from git history if needed); zero functional risk if truly dead.
- **Gate:** user confirms "highway-ui is superseded and not coming back".

**A.3 — File-size CI guardrail (part of Bucket C; listed here for timing).** Adding the guardrail before the refactor means the refactor can use shrinking the exemption list as its own progress signal. See §5.

### 3.2 Bucket B — Post-v0.1 structural refactor

Not pre-launch. Mid-merge is the worst moment. Done as a single `refactor/file-splits` branch after `dev → main` ff, so it's one blame event and no rebase churn for other in-flight work. Each file split is behavior-preserving — rearrangement only — which means the PR reviews as "module moves, signatures unchanged".

**B.1 — `init.rs` (2139 lines).** Split into:
- `runtime.rs` — `Runtime` struct, `init()`, lifecycle, `fan_out_event()` dispatcher (~400 lines)
- `agent_service.rs` — `handle_agent_request()` match block (~400 lines)
- `highway_service.rs` — `handle_highway_request()` match block (~600 lines)
- `coordinator_service.rs` — `handle_coordinator_request()` match block (~500 lines)
- `conversions.rs` — the `*_to_proto` helpers landed in §11.4 + budget/envelope helpers (~240 lines)

§11.4's fix already carved the seed (6 helper functions clustered together). Target: no file >800 lines; average ~440.

**B.2 — `session_monitor.rs` (2120 lines).** Split by stream driver: `trail_driver.rs` + `gate_driver.rs` + `escalation_driver.rs` + `workspace_driver.rs` + `monitor.rs` (spawn/handle/teardown). Each driver today is a cohesive block in one file; this is mechanical extraction. Target: no file >700 lines.

**B.3 — `session_launcher.rs` (1877 lines).** Split by launch stage: `submit.rs` + `decompose.rs` + `dispatch.rs` + `rollback.rs` + `launcher.rs` (orchestrator). Aligns with W2's conceptual flow. Target: no file >600 lines.

**B.4 — `routes/highway.rs` (1832 lines).** Split by REST resource: `routes/highway/gates.rs` + `routes/highway/escalations.rs` + `routes/highway/envelopes.rs` + `routes/highway/pending.rs` + `routes/highway/mod.rs` (shared helpers + router wiring). Target: no file >600 lines.

**B.5 — `config.rs` (1748), `recovery.rs` (1485), `rest_gateway.rs` (1202), `routes/sessions.rs` (1181), `tools/execution.rs` (1137).** Same pattern — each splits along natural internal boundaries that are already visible today.

Effort estimate for B.1–B.5 combined: **~8–12 h**, most of which is test-file re-pathing, `pub(crate)` visibility tweaks, and import fix-ups. The logic doesn't change. Done as one reviewable PR, landing a single squash-merge.

**What NOT to split:**
- `tests.rs` monoliths — one test module per crate is conventional and searchable. Scrolling tests is a non-event.
- Generated files — `types.ts`, `v1.py`, `primitives_pb.ts`. Those regenerate on schema change.
- `middleware.rs` (955), `profiles.rs` (864), `execution.rs/registry.rs/resilience.rs` siblings — under the 1000-line threshold. Not urgent.

### 3.3 Bucket C — Prevention

**C.1 — CI file-size lint (Rust).**

Add a job to `ci-lint.yml`:
- **Warn** on any `.rs` file >1000 lines (non-test, non-generated).
- **Fail** on any such file >1500 lines, *unless* it's in a top-level `.file-size-allowlist` file.

The allowlist is the debt list. Bucket B's 11 files go in on day 1. Removing an entry is free; adding one requires an explicit PR change that reviewers see. The refactor branch shrinks the allowlist as its own progress signal — the CI fails closed when a refactor accidentally skips a file.

**C.2 — CI file-size lint (TypeScript).**

Same pattern, tighter thresholds: warn >500 lines, fail >1000. Frontend monoliths are worse UX than backend ones (React hot-reload + JSX + hook deps amplify the cost of navigation debt).

Current TS files over 1000 lines in production code: **one** (`Wizard.tsx` at 806 is under the fail threshold; `types.ts` at 2907 is generated and allowlisted). The TS side is already in good shape — the guardrail locks that in.

**C.3 — Process note in SEED.md / CLAUDE.md.**

One-liner at the relevant policy section: "Production source files >1000 lines are a refactor signal, not a norm. CI warns; >1500 fails without explicit allowlisting. See `impl/tech-debt-2026-04-18.md` §5."

### 3.4 Explicitly out of scope

- `target/` size (16 GB) — standard cargo build cache; `sccache` is an orthogonal optimization.
- `.git/` size (429 MB) — expected for an active project; `git clone --depth 1` gives contributors 12 MB.
- `lucide-react` 34 MB in node_modules — tree-shaken at build, not user-facing. Dev-env only. Addressable later by switching icon strategy, but not a priority.
- Rust transitive dep counts — dominated by tonic / tokio / axum / sqlx. Each could be audited individually, but the marginal reduction per dep is tiny and the audit time is large.
- Python SDK (3,755 lines) — already small, already isolated.

## 6. What this doc is not

- Not a license to rip up the tree pre-launch. Bucket B is explicitly deferred.
- Not a claim that user-facing size is a problem. It isn't. Binaries are 11–17 MB stripped; SPA is 384 KB gzip-ready.
- Not a hit-list. The allowlist is how refactor progress is measured, not a shame table.
- Not exhaustive. A post-launch pass may find more — the CI lint surfaces them automatically.

## 7. Open questions for the user

1. **highway-ui: delete or keep?** If delete, pre-launch. If keep, it needs a `wcon-vision`-level justification in the allowlist.
2. **File-size lint thresholds: 1000/1500 for Rust, 500/1000 for TS — agree?** These are my read of the data; adjust if different experience elsewhere suggests otherwise.
3. **Is the refactor (Bucket B) a single PR or one-per-file?** Single PR = clean blame event but huge diff; per-file PRs = reviewable chunks but more rebase churn. My default vote: single PR on dedicated branch, squash-merge.
